# 饮食采集设计

## 设计目标

优先提高“每天真的记下来”的概率，再提高营养估算精度。

减脂顾问最危险的失败方式不是少一个营养字段，而是记录流程太重，用户第三天就停止使用。

## 双路径

### 1. 快速手工记录

必填：

- 时间；
- 餐次；
- 一句食物和份量描述。

可选：

- 热量；
- 蛋白质、碳水、脂肪；
- 数字可信度；
- 外卖、少油、剩余比例等备注。

原则：不知道就留空。食物描述仍可用于识别漏记、餐次和行为模式。

### 2. 照片辅助记录

配置图片分析接口后：

- 上传一张整餐照片；
- 返回食物构成、份量区间和营养区间；
- 明确照片不能确定的油、糖、酱汁和隐藏配料；
- 不保存原始照片，只保存文字结果。

照片路径减少输入负担，但不能替代称重或包装营养标签。

## 当前数据模型

两种路径都写入 `nutrition_logs`：

- `source=quick_manual`：手工记录；
- `source=photo_ai`：照片辅助；
- `raw_json`：描述、置信度、备注或分析详情。

不另建平行饮食数据库，避免统计口径分裂。

## 覆盖度指标

近 7 天：

- `logged_days`：至少有一条记录的天数；
- `record_count`：总记录条数；
- `coverage_pct`：记录天数 / 7；
- `logging_confidence`：低、中、高。

初始规则：

- 0–1 天：低，只能给目标；
- 2–4 天：中，可观察漏记/餐次模式；
- 5–7 天：高，可开始分析摄入模式，但营养数字仍有估算误差。

## 后续优先级

1. 最近餐食一键复制；
2. 常用餐模板；
3. 语音转文字；
4. 包装条码/营养标签；
5. 以周为单位的漏记提醒；
6. 用户确认后再把照片建议转为结构化数字。

每项功能都应通过“是否提高 7 天记录率”验证，而不是只看功能数量。
