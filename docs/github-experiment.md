# GitHub 双项目实验

## 假设

两个仓库服务不同需求，都值得独立发布：

### Mi Fitness Data Bridge

用户任务：拥有、导出并复用自己的小米健康数据。

潜在传播优势：

- 问题边界清晰；
- 开发者能快速集成；
- 中国区 Mi Fitness 数据访问内容相对稀缺；
- JSON/CSV/Python/MCP 都可独立产生价值。

### Health Advisor

用户任务：把体脂、睡眠、运动和饮食组合起来，持续执行减脂调整。

潜在长期优势：

- 解决完整结果而不只是数据访问；
- 能形成周报、留存和服务价值；
- 饮食记录和行动反馈可建立产品闭环。

## 不提前争论谁“应该”高星

分别发布，保持清晰互链，让用户用行为投票。不能把两个仓库塞回一个项目来追求表面完整，因为这会同时模糊开发者工具和终端产品的定位。

## 发布页对照

| 项目 | README 首屏 | 第一条成功路径 | 明确不做 |
|---|---|---|---|
| Bridge | 导出你自己的 Mi Fitness 数据 | setup → sync → export | 不做减脂建议 |
| Advisor | 把已有数据变成每周减脂行动 | 安装 → 接数据 → 记录饮食 → 看周建议 | 不复制连接器、不做医疗 |

## 90 天指标

### Bridge

- GitHub Stars；
- 成功同步次数（由用户主动上报或匿名可选统计，默认不遥测）；
- 设备/地区兼容报告；
- 外部 Issue、PR、贡献者；
- 被其他项目依赖或引用的次数。

### Advisor

- 成功安装；
- 7 天饮食记录覆盖率；
- 周报生成率；
- 4 周留存；
- 建议执行反馈；
- 用户是否愿意为安装、定制或持续服务付费。

## 判断原则

> Star 决定传播；真实安装和贡献决定生态价值；留存和付费决定用户问题是否被解决。

可能出现的结果：

1. Bridge 高星、Advisor 低留存：数据需求真实，但顾问体验需要重做；
2. Bridge 平稳、Advisor 高留存：完整闭环更有价值；
3. 两者都增长：形成基础设施 + 应用的生态；
4. 两者都弱：需要重新验证用户、安装门槛和 Xiaomi 连接稳定性。

## 发布纪律

- 使用合成数据截图；
- 不上传真实 token、数据库、日志或个人体脂数据；
- 两个仓库各自有独立 Issue 标签和 Roadmap；
- Bridge 的连接器修复只在 Bridge 实现；
- Advisor 通过版本依赖获取修复，不复制补丁；
- README 明确非官方、实验性和非医疗边界。
